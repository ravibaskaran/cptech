# Requirements: Justo CP App BRD

**Defined:** 2026-05-30  
**Core Value:** The BRD must make the CP network lifecycle explicit enough that Justo can scope, compare, and negotiate the CP app as a business operating system rather than as a generic mobile CRM add-on.

## v1 Requirements

### Document Foundation

- [ ] **DOC-01**: Stakeholder can understand the BRD purpose, audience, scope, and intended decisions from the opening sections.
- [ ] **DOC-02**: Stakeholder can distinguish confirmed local-document facts, market research inferences, and open assumptions through confidence labels or equivalent evidence notes.
- [ ] **DOC-03**: Stakeholder can trace the BRD back to the source corpus: Manthan proposal, Phase 1/2/2.4/3 SoWs, Auum proposal, TSPL proposal, I9 proposal, and the existing business brief.
- [ ] **DOC-04**: Stakeholder can see explicit out-of-scope boundaries for this BRD, including no app implementation plan, no final vendor award, and no detailed API design.

### Business Objectives

- [ ] **BUS-01**: Stakeholder can understand Justo's strategic objective to become a large regional CP in Maharashtra first and later expand across India.
- [ ] **BUS-02**: Stakeholder can understand why the CP app must be treated as a CP operating system rather than only a mobile CRM interface.
- [ ] **BUS-03**: Stakeholder can see the three operating loops: CP acquisition/enablement, transaction execution, and trust/compliance.
- [ ] **BUS-04**: Stakeholder can review proposed success metrics for the BRD and for the eventual CP app business outcome.

### Manthan Baseline

- [ ] **MANT-01**: Stakeholder can see what Project Manthan already covers across CRM, lead management, CP management, portals, KYC/payment/token workflows, communications, dashboards, and integrations.
- [ ] **MANT-02**: Stakeholder can see delivered or scoped capabilities by phase: Phase 1, Phase 2, Phase 2.4, Phase 3, and I9 CP Tech proposal.
- [ ] **MANT-03**: Stakeholder can distinguish capabilities to reuse, configure, extend, or add outside current Manthan scope.
- [ ] **MANT-04**: Stakeholder can identify source-of-truth questions for CP, CP employee, lead, project, inventory, booking, invoice, and payout.

### Personas

- [ ] **PERS-01**: Stakeholder can review all core personas: Justo leadership, CP sourcing head, RM/sourcing employee, sales/admin ops, finance, developer/project team, CP owner, CP employee/agent, CP telecaller, buyer/customer, and compliance/support.
- [ ] **PERS-02**: Stakeholder can see each persona's goal, in-app responsibilities, outside-app responsibilities, key pain points, and success indicators.
- [ ] **PERS-03**: Stakeholder can identify which personas are v1-critical versus supporting or future personas.

### Lifecycle Deep Dives

- [ ] **LIFE-01**: Stakeholder can review the Justo CP sourcing lifecycle from CP prospecting through offboarding.
- [ ] **LIFE-02**: Stakeholder can review the CP firm lifecycle from registration through renewal, expansion, suspension, or offboarding.
- [ ] **LIFE-03**: Stakeholder can review the CP employee lifecycle from invite/import through deactivation and lead reassignment.
- [ ] **LIFE-04**: Stakeholder can review the lead ownership lifecycle, including lead capture, dedupe, lock, conflict, expiry, override, dispute, and audit evidence.
- [ ] **LIFE-05**: Stakeholder can review the site-visit lifecycle, including schedule, proof, buyer feedback, site outcome, and commission eligibility linkage.
- [ ] **LIFE-06**: Stakeholder can review the commission/payout lifecycle, including rule, booking validation, invoice, GST/TDS, finance approval, payment, reconciliation, and dispute.

### Pain Points And Opportunities

- [ ] **PAIN-01**: Stakeholder can review key Indian CP pain points: inventory trust, lead disputes, payout opacity, fragmented communication, compliance burden, low lead quality, CP employee control, marketing attribution, site-visit proof, and buyer trust.
- [ ] **PAIN-02**: Stakeholder can map each pain point to technology-addressable capabilities.
- [ ] **PAIN-03**: Stakeholder can see which pain points are currently addressed by Manthan, partially addressed, or not yet addressed.
- [ ] **PAIN-04**: Stakeholder can see recommended differentiators: CP trust score, payout promise, inventory freshness, CP Academy, claim-safe collateral, RM field productivity, and dispute-grade evidence.

### Capability Requirements

- [ ] **CAP-01**: Stakeholder can review a capability map grouped by onboarding/compliance, project/inventory, lead ownership, communication, site visits, booking visibility, payout ledger, CP employee management, sourcing/RM operations, analytics, admin, and support.
- [ ] **CAP-02**: Stakeholder can see an MVP recommendation that prioritizes onboarding, lead lock, inventory, site visit, booking visibility, payout ledger, and sourcing/RM dashboard.
- [ ] **CAP-03**: Stakeholder can see v2/deferred capabilities, including AI voice, campaign automation, CP microsites, advanced workforce intelligence, and broader marketplace/network features.
- [ ] **CAP-04**: Stakeholder can see acceptance criteria for critical capabilities that should appear in any SoW annexure.

### Vendor Gap Mapping

- [ ] **VEND-01**: Stakeholder can compare Auum, TSPL/Triazine, and I9/Indexnine against the same capability matrix.
- [ ] **VEND-02**: Stakeholder can identify gaps in each written proposal without overclaiming vendor inability.
- [ ] **VEND-03**: Stakeholder can compare vendor fit across Manthan integration, CP lifecycle depth, lead/payout trust, delivery risk, commercial/IP/support, AI, and mobile/app readiness.
- [ ] **VEND-04**: Stakeholder can review a vendor clarification checklist suitable for follow-up conversations or SoW annexure drafting.

### Review Readiness

- [ ] **REV-01**: Stakeholder can review open questions, risks, dependencies, and decisions needed before vendor alignment or SoW finalization.
- [ ] **REV-02**: Stakeholder can use the BRD to run an internal review with Justo leadership, CP sourcing, sales/admin ops, finance, and product/technology stakeholders.
- [ ] **REV-03**: Stakeholder can identify the next artifact after the BRD: SoW annexure, vendor scorecard, CP interview guide, or product requirements document.

## v2 Requirements

### Field Validation

- **VAL-01**: Stakeholder can review findings from 8-12 CP/RM interviews in Maharashtra.
- **VAL-02**: Stakeholder can compare BRD assumptions against interview evidence.

### Procurement Support

- **PROC-01**: Stakeholder can use a weighted vendor scorecard with explicit scoring evidence.
- **PROC-02**: Stakeholder can review vendor responses to the clarification checklist.

### Technical Annexure

- **TECH-01**: Stakeholder can review system integration diagrams, API/domain ownership, event flows, and data model implications.
- **TECH-02**: Stakeholder can review a delivery plan for the selected vendor or internal implementation team.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Building the Android/iOS app | This project is currently for BRD and planning artifacts. |
| Final vendor selection | BRD can support decision-making, but procurement requires stakeholder approval. |
| Low-level API specification | Needs technical discovery after BRD agreement. |
| Detailed UX wireframes | BRD should define business flows and capability needs first. |
| Production delivery roadmap for app implementation | Should follow BRD approval and SoW/vendor decisions. |

## User Stories

- As a Justo executive, I can understand why the CP app is a strategic CP operating system so that I can evaluate investment and vendor direction.
- As a CP sourcing leader, I can review CP sourcing, onboarding, activation, and retention requirements so that the app supports real field operations.
- As a Justo finance stakeholder, I can review commission/payout lifecycle requirements so that payout transparency and controls are not under-scoped.
- As a product/technology stakeholder, I can distinguish Manthan reuse/configuration/extension/addition so that the app scope is grounded in the existing platform.
- As a procurement/vendor-management stakeholder, I can compare vendor proposals against a common capability matrix so that follow-up negotiations are specific.

## Acceptance Criteria

- The BRD draft includes all v1 requirement categories.
- The BRD draft separates facts, inferences, and open questions.
- The BRD draft includes a vendor matrix for Auum, TSPL, and I9.
- The BRD draft includes at least one lifecycle diagram or structured lifecycle table for Justo CP sourcing, CP firm, CP employee, lead ownership, site visit, and payout.
- The BRD draft includes an MVP recommendation and deferred capability list.
- The BRD draft can be reviewed without reading every original proposal first.

## Definition of Done

- BRD draft is written in Markdown.
- All v1 requirements are addressed or explicitly marked as unresolved.
- Open questions and assumptions are listed.
- Source documents are referenced.
- Stakeholder review checklist is included.
