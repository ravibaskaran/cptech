# Adversarial Analysis & Risk (Red Team) Review — Product Architecture Council

## Review Summary

The Red Team review evaluates the Justo CP App from the perspective of a malicious actor (an adversarial Channel Partner, a compromised Relationship Manager, or an external attacker). The current system designs contain significant vulnerabilities that can be exploited for financial gain, lead snatching, and data theft. The offline-first design allows suspended users to access sensitive data indefinitely unless a secure purge is implemented. The geofenced check-in system can be easily bypassed using GPS spoofing, and the lack of automated bank detail validation creates a direct route to payout fraud. This review outlines these attack vectors and recommends security mitigations.

---

## Adversarial Attack Trees

### 1. Attack Vector: GPS Spoofing for Site-Visit Fraud
* **Threat Narrative:** CPs are paid commissions based on verified site visits. A malicious CP agent wants to claim site visit attribution without actually bringing the buyer to the physical location.
* **Mechanism:** The attacker uses a standard Android developer utility or a mock location app to spoof their device's GPS coordinates to match the project site. They then click "Verify Check-in" from their couch.
* **Likelihood:** High
* **Impact:** High (Direct financial loss through fake commission payouts and wasted sales resource time)
* **Current Mitigation:** `Justo_CP_App_PRD.md` §7.7 (PRD-FR-050, line 462) mentions geofencing but relies on client-side GPS verification.
* **Recommended Mitigation:** Implement multi-factor verification: (1) Enforce **Mock Location Detection** in the KMP Android build, blocking check-in if mock providers are active, (2) Combine geofencing with an **OTP or QR Code** generated by the Justo site-desk terminal (the buyer or site executive must scan the CP's phone to verify physical presence), (3) Cross-reference check-in coordinates with network cell tower IDs.

### 2. Attack Vector: Lead Snatching via Phone Number Mangle
* **Threat Narrative:** A CP wants to bypass the lead lock on an existing active lead registered by another firm.
* **Mechanism:** If the lead locking deduplication checks only match on exact 10-digit phone numbers, the malicious CP registers the lead as "+91 98765 43210", "09876543210", or "9876543210 ext 1". Alternatively, they change one digit or register using a family member's number.
* **Likelihood:** High
* **Impact:** High (Damages CP trust, creates disputes, and leads to double-brokerage claims)
* **Current Mitigation:** `Justo_CP_App_PRD.md` §7.5 (PRD-FR-031, line 429) mentions deduplication checks but does not define matching rules.
* **Recommended Mitigation:** Enforce strict backend phone normalization (using Google's libphonenumber library) to strip all non-numeric characters and country codes before running deduplication. Implement fuzzy matching on lead names and email addresses. If a phone number is registered within a 30-day window, flag a conflict and require RM manual override.

### 3. Attack Vector: Suspended User Data Exfiltration (Offline Cache Leak)
* **Threat Narrative:** A CP employee is terminated by the CP Owner or suspended by Justo for fraud, but wants to steal the firm's lead database before losing access.
* **Mechanism:** The user switches their phone to airplane mode to block the remote deactivation WebSocket command. Since the client is offline-first, the local SQLite database remains fully readable. The attacker uses a rooted Android device to copy the SQLite file or uses screen-scraping tools to copy the leads.
* **Likelihood:** Medium
* **Impact:** High (PII theft, DPDPA violation, loss of proprietary business data)
* **Current Mitigation:** `Justo_CP_App_PRD.md` §15 (lines 1073–1075) notes that offline access by suspended users is an open question.
* **Recommended Mitigation:** Implement **Time-to-Live (TTL) Session Keys** for local SQLite encryption. The local database encryption key (SQLCipher) must be rotated and refreshed every 24 hours via API. If the client cannot connect to the server within 24 hours to validate token status and fetch the fresh decryption key, the local session expires and the SQLite data remains locked and inaccessible.

### 4. Attack Vector: API Manipulation to Bypass RBAC
* **Threat Narrative:** A CP Employee wants to view payout details that are restricted to the CP Owner.
* **Mechanism:** The user intercepts the mobile outbound traffic (e.g., using a proxy tool like mitmproxy) and modifies the API requests, changing user role parameters or directly hitting the `GET /payouts` endpoint with their employee token.
* **Likelihood:** Medium
* **Impact:** High (Breach of financial confidentiality, unauthorized access to sensitive firm metrics)
* **Current Mitigation:** `Justo_CP_App_PRD.md` §9 (Source-of-Truth Rules, line 819) notes that roles must be enforced server-side.
* **Recommended Mitigation:** Enforce **JWT-Claims Validation** on every single backend endpoint. The API must decode the token, read the roles/permissions from the secure claim payload, and validate authorization at the controller level (e.g., using NestJS guards). Never trust client-sent role variables or query parameters.

### 5. Attack Vector: KYC Upload Malicious Payload (Admin Terminal Takeover)
* **Threat Narrative:** An attacker wants to compromise the internal Justo administrative systems to steal data or alter payout details.
* **Mechanism:** The attacker registers as a CP and uploads a malicious PDF (containing an embedded zero-day exploit or PDF-based phishing payload) under the "RERA Certificate" or "PAN Card" upload fields. When a Justo admin downloads and opens the document on their workstation, the exploit executes.
* **Likelihood:** Low
* **Impact:** Critical (Full system takeover, compromise of internal networks)
* **Current Mitigation:** `Justo_CP_App_PRD.md` §7.13 (PRD-FR-079, line 519) mandates file type limits, but does not mention server-side malware scanning.
* **Recommended Mitigation:** Set up an **asynchronous ClamAV malware scanner** inside the object storage pipeline. Any uploaded file must remain in a `QUARANTINED` storage bucket. The document verification queue will only display the file to the administrative user after the virus scanner returns a clean scan result and copies the file to the `APPROVED` bucket.

### 6. Attack Vector: Denial of Service via Sync Storm
* **Threat Narrative:** An attacker wants to disrupt Justo's operations during a major sales event.
* **Mechanism:** The attacker writes a script to trigger thousands of fake local writes (e.g., mock lead submissions or site visit schedules) and flood the PowerSync synchronization engine, overloading the active-active API nodes and the Primary Postgres DB.
* **Likelihood:** Low
* **Impact:** High (System slowdown, disruption of field RM and CP operations)
* **Current Mitigation:** `ARCHITECTURE.md` §2.2 lists Traefik and managed load balancer, but does not define rate-limit policies for WebSockets.
* **Recommended Mitigation:** Enforce strict **Connection Limits** on Traefik and logical partition rules on Postgres. Implement rate limits on the WebSocket sync gateway (e.g., maximum 5 write sync events per client per second). Use PostgreSQL resource pools to isolate the API connections from the sync queue polling connections.

## Red Team Recommendations

### R1. Mandate Dual-Factor Verification for Site Visits (Priority: High)
Do not rely on geofencing alone for site visit validation. Enforce GPS location checks *in combination with* a site-desk physical QR code scan or an OTP sent to the Buyer's mobile phone at the site desk.

### R2. Secure Offline SQLite Data (Priority: High)
Implement the 24-hour TTL session key rotation policy for the SQLCipher local database. Ensure that a remote suspension event forces a local database wipe command when the app is next online.

### R3. normalization on Lead Inputs (Priority: High)
Normalize all phone numbers and email addresses on the server side before running database deduplication checks, to prevent malicious lead snatching through formatting bypasses.

---

## Overall Security Confidence

**Confidence Score: Low-to-Moderate**

**Justification:** While the business permissions mapping is solid, the lack of local database cache encryption, the ease of bypassing client-side geofencing, and the complete absence of data privacy notices under DPDPA represent severe vulnerabilities. Resolving these threat vectors is essential to protect the platform from fraud and regulatory liability.
